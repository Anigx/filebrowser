# Passwordless Security-Key Login Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let each File Browser user replace their password with a FIDO2 key and recover intentionally, then publish a tested release of the fork.

**Architecture:** Keep the built-in JSON auth mode and add login and step-up WebAuthn ceremonies at the HTTP boundary. A private Bolt authentication record owns the credential set and session epoch; credential changes update that record and the user row in the same transaction. The Vue login, profile, and user editor use the existing session and settings conventions.

**Tech Stack:** Go 1.26 toolchain, `go-webauthn/webauthn`, Storm/bbolt, Vue 3/TypeScript, Vitest, Chromium virtual authenticator, GitHub Actions and GoReleaser.

**Spec:** [`docs/superpowers/specs/2026-11-26-webauthn-login-design.md`](../specs/2026-11-26-webauthn-login-design.md)

## Global Constraints

- Opt-in per account, JSON authentication only; existing users without a key still use passwords. Keep reCAPTCHA enforcement when configured.
- One explicit HTTPS origin, exact hostname RP ID; permit `http://localhost` with an optional port for tests. Require user verification; do not require discoverable credentials or Yubico attestation.
- No password-only access after enrollment. Remove the last credential only with a newly set password meeting the instance's minimum and differing from the retired password.
- Fresh proof for self-service security-key actions and admin changes; no admin enrollment on behalf of someone else. No secrets in logs, command-line arguments, JWTs, or generic user payloads.
- Commit, push and publish only to `Anigx/filebrowser`. No upstream registries, no live deployment and no release when required verification is red.

## Review Focus

- Stale generic user saves must not undo a credential transition, and two edits using the same epoch cannot both commit (Task 1).
- `https://files.example` and `https://files.example:443` are the same origin; a subdomain, origin with a path, or spoofed proxy header is not (Task 2).
- A sign-in assertion is not a fresh approval for an account operation; a proof for one admin target must not authorize another (Task 3).
- An administrator must still be able to manage an enrolled, password-locked user without assigning a password in the standard user editor (Tasks 3–4).
- Deployment and release checks must run on the commit actually tagged, and skipped tests never count as passed (Task 5).

### Task 3: Browser ceremonies and authorized operations

**Files:** Create `http/webauthn.go`, `http/webauthn_challenges.go`, `http/webauthn_test.go`; modify `http/http.go`, `http/data.go`, `http/users.go`, `http/auth.go`, `auth/json.go`.

**Interfaces:** All ceremony endpoints are POST with JSON; response envelope `{id, publicKey}`; finish payload `{id, credential}`. `POST /api/webauthn/login/start` takes `{username, recaptcha}` and `POST /api/webauthn/login/finish` returns the existing token text; `GET /api/webauthn/users/{id}` returns `{keys:[{id,label,createdAt}]}` to self/admin; no credential material in that response except the opaque IDs used for management. `POST /api/webauthn/verify/start` takes `{action,targetID,keyID?}`; `POST /api/webauthn/verify/finish` returns `{proof}`. `POST /api/webauthn/register/start` accepts `{label,currentPassword,proof?}`; `POST /api/webauthn/register/finish` commits a key and returns `204`. `POST /api/webauthn/users/{id}/remove` takes `{keyID,currentPassword?,proof?,newPassword?}`; omit `keyID` to switch back and remove all. Reference existing user mutations via actions `create-user`, `update-user`, `delete-user`; use `add-key`, `remove-key`, and `reset-keys` for credential operations, and carry `proof` alongside `current_password` on existing routes.

- [ ] Add `TestWebAuthnChallengeLifecycle`, `TestWebAuthnLoginAuthorization`, and `TestWebAuthnCredentialManagement`: assert valid UV signatures authenticate only the owner; wrong origin, expired or replayed challenge, and failed verification issue no token; missing reCAPTCHA cannot start login where required; retired password fails after enrollment and after losing one of two keys; last-key removal without a distinct policy-compliant password fails; a fresh key or password proof works only for its bound actor, session, target and action. Assert a locked account can update backup keys but cannot switch mode. Verify non-admins cannot manage other accounts and admins cannot enroll for others. Use locally generated test credentials and/or the library's authenticator test fixtures for positive verification, not an external service.
- [ ] Run `go test ./http -run 'TestWebAuthn|TestKeyEnrollmentRevokesSession'`; expect red.
- [ ] Implement a per-handler cache with 1,024 active entries, 2-minute ceremony lifetimes, 60-second proof lifetimes and atomic consume; expired entries are pruned before accepting new ones, and full capacity refuses new work. Constrain anonymous requests with bounded bodies, one-time state and a bounded attempt budget that does not trust client-supplied IP headers. Reject cross-origin request headers against configured origin (allow command-line clients without the header only when they still satisfy protocol proof). For enrollment generate a random 32-byte stable handle, use cross-platform and UV-required registration with `residentKey: discouraged` for username-first login, and use existing credential exclusions. Bind management state to the exact action, actor, session, target, relevant epochs and key ID; recheck after verification before mutation. Invoke the library finish methods; use library backup/clone-warning semantics and persist authenticator metadata only with a current account/credential snapshot. Share reCAPTCHA checks with JSON auth. Generic anonymous failures must return equivalent error bodies and must never mint a session or log raw WebAuthn payloads.
- [ ] Wire the endpoints and sensitive user create/update/delete checks. Preserve current password behavior for unenrolled callers. Track whether an existing update explicitly requests a password change; an enrolled target can change mode only through the deliberate reset endpoint. Require fresh own-key confirmation for an enrolled caller and fresh password for an unenrolled admin resetting another user's keys. Do not accept a key management proof for any existing generic action. Mint the existing JWT only after a valid login assertion; reject stale epochs at final mutation and use latest loaded user state when minting. Use `Cache-Control: no-store` on ceremony responses.
- [ ] Run the focused command, then `go test -race ./auth ./http ./storage/bolt ./sessions` on a race-supported environment; expect all pass. Commit `feat(auth): add passwordless login, key management and admin reset`.
